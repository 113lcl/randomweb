Why we stopped designing in components and started designing in systems.

Elena Kowalska
Co-Founder, Creative Director

On this page

𝕏 in

For years, our design process started the same way every agency's does: open Figma, create a new frame, start drawing a homepage. Components got built along the way — a button here, a card there — assembled reactively as the screens demanded them. It felt productive. It was, in fact, quietly expensive.

The problem with components-first

Designing screen-by-screen means every decision is made in the context of one page, for one moment. A button gets a border radius of 8px because it looked right on the homepage hero. Three screens later, a different designer creates another button at 12px because that's what felt right there. Neither designer is wrong — but multiply that by 40 screens and six months, and you get a product that reads like it was designed by six different studios, because in a sense, it was.

We noticed this most acutely on our larger product engagements. A feature that should have taken three days of design work was taking five, and most of the extra time wasn't spent solving new problems — it was spent re-deciding problems we'd already solved, just in a slightly different context.

Making the shift

The fix wasn't a new tool. It was a sequencing change: define the system before the screens exist to use it. Concretely, that means the first week of any product engagement is now spent almost entirely away from full-page compositions. We build:

  • A constrained type scale — six sizes, not sixteen.
  • A spacing scale based on a single base unit, so every margin and padding is a multiple of one number.
  • Color roles, not color names — "surface," "border," "accent" — mapped to values that can shift without renaming anything downstream.
  • Core interactive components (button, input, card, modal) built to handle every state — hover, focus, disabled, loading — before a single real screen references them.

Tokens before pixels

The single highest-leverage habit has been designing in tokens before touching pixels. When "primary action color" is a token rather than a hex value pasted into forty different layers, changing brand direction two weeks before launch — which happens more often than clients like to admit — becomes a five-minute fix instead of a five-day one.

The system isn't a constraint on creativity. It's what buys you the time to be creative about the 5% of the product that actually needs a fresh idea, instead of spending it all on the other 95%.

This also changes how design reviews feel. Instead of debating whether this particular button should be 8px or 12px radius, the conversation moves to whether the flow makes sense, whether the copy is honest, whether the feature solves the actual problem. The system absorbs the small decisions so the room can focus on the big ones.

What changed

Since adopting this sequencing across client work in 2024, we've tracked design-hours-per-shipped-screen across comparable engagements. The number dropped by roughly 30% on average, with the effect compounding on longer projects — the Aurora rebuild, for instance, saw new screens in month three take almost half the design time of screens in month one, because the system had matured enough to answer most small questions on its own.

Engineering handoff improved too. When a design system maps cleanly onto a component library, the conversation with engineers shifts from "what does this look like" to "does this match," which is a much faster conversation to have.

Advice if you're starting

Start smaller than feels comfortable. You don't need forty documented components before you can design a single real screen — you need the five or six that will appear everywhere, built properly once. Everything else can be extended from those foundations as real screens demand them, but now within constraints instead of inventing new ones each time.

And resist the urge to make the system perfect before using it. Systems get better by being stress-tested against real screens, not by being polished in isolation. Ship the first version, let real work push on its edges, and revise deliberately rather than endlessly.
