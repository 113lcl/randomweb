Shipping motion-heavy sites without tanking Core Web Vitals.

Amara Diallo
Senior Frontend Engineer

On this page

𝕏 in

Every client wants a site that feels alive. Almost none of them are willing to trade page speed for it — and they shouldn't have to. We've shipped dozens of sites now with cursor effects, scroll-triggered reveals, magnetic buttons and canvas backgrounds while holding Lighthouse performance scores above 95. Here's how.

Set a motion budget

Before any animation gets designed, we set a budget: how many concurrently-animating elements the page is allowed at once, and on what properties. Almost everything on a Pulsar site animates only transform and opacity — properties the browser can animate on the compositor thread without triggering layout or paint. Anything that would animate width, top, or box-shadow spread gets redesigned to use a transform-based equivalent instead.

Stay on the compositor

The single biggest performance lever in motion design is avoiding layout thrashing — style changes that force the browser to recalculate geometry on every frame. We promote elements that animate frequently onto their own composite layer with will-change, used sparingly since overuse burns memory, and we batch DOM reads and writes so we're never reading getBoundingClientRect() immediately after writing a style in the same frame.

A 60fps animation on the compositor thread costs less battery and CPU than a 30fps animation running on the main thread. Smoothness and efficiency aren't in tension here — they're the same fix.

Observe, don't poll

Scroll-triggered reveals are one of the most common motion patterns on our sites, and also one of the easiest to implement badly — a scroll event listener recalculating positions on every pixel of movement will visibly janky even a simple fade-in. We use IntersectionObserver everywhere instead, which lets the browser notify us only when an element's visibility actually changes, off the main thread's critical path.

Fonts and layout shift

Custom display typefaces are core to a distinctive brand, but they're also a classic source of Cumulative Layout Shift if handled carelessly. We self-host or preconnect to font providers, set font-display: swap deliberately, and size fallback fonts with matched metrics so body copy doesn't visibly reflow once the real typeface loads in.

Our pre-launch checklist

  • Every animation profiled in Chrome DevTools' Performance panel for dropped frames.
  • All scroll listeners replaced with IntersectionObserver where possible.
  • Images served in modern formats, sized to their actual rendered dimensions.
  • Lighthouse run in CI on every pull request, with a hard budget that fails the build below 90.
  • prefers-reduced-motion respected everywhere — motion is a delight, never a requirement.

None of this requires exotic tooling. It requires treating performance as a design constraint from day one, the same way we treat accessibility or responsive layout — not a cleanup pass at the end.
